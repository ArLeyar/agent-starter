# 01. Сервер: проверка системы, первый вход, защита

Цель шага: сервер на Ubuntu 24.04 или 26.04, на который можно зайти только владельцу по ключу, с проверенным аварийным входом, автоматическими обновлениями безопасности и защитой от подбора пароля.

Обозначения в командах:

- `<IP-адрес сервера>`: адрес из письма Contabo или из панели.
- `<имя>`: логин нового пользователя на сервере, например `kostya` или `andrey` (латиница, строчные).
- Каждый блок команд помечен комментарием, кто его выполняет:
  - `# ноутбук`: терминал ноутбука владельца;
  - `# администратор`: сервер, под `root` или под `<имя>` с `sudo`;
  - `# человек`: действие, которое выполняет только человек (пароль, панель Contabo, консоль VNC). Агент, ведущий установку, здесь останавливается и ждёт.
- Для автоматического выполнения команды даются с явным пользователем и абсолютными путями. Интерактивные редакторы (`nano`) заменены записью через `tee`.

Термины:

- **VPS** (virtual private server): арендованный виртуальный сервер, на котором работает своя копия Ubuntu.
- **SSH**: защищённое соединение с сервером через терминал. После входа команды выполняются на сервере, а не на своём компьютере.
- **root**: встроенный администратор Ubuntu с неограниченными правами. Работа под root опасна: любая опечатка в команде удаляет или ломает систему.
- **sudo**: приставка к команде, которая выполняет её с правами администратора для обычного пользователя. Пароль пользователя запрашивается при первом `sudo` за сессию.
- **Ключ SSH**: пара файлов. Приватный (`id_ed25519`) хранится только на своём компьютере и никому не передаётся. Публичный (`id_ed25519.pub`) кладётся на сервер. Вход происходит без пароля, по совпадению пары.

## Предупреждения

1. **Пароль root сменить сразу после первого входа** (шаг 3). Пароль, заданный в панели Contabo, при передаче сервера мог пройти через почту, мессенджер или голову другого человека. Пока он остаётся прежним, сервер открыт всем, кто его знал.
2. **Сервер передан другим человеком: после шагов 5 и 6 войти на него сможет только владелец ключа.** Это нужное свойство, а не побочный эффект. Если ключ потерян, доступ восстанавливается через консоль VNC в панели Contabo, без переустановки (раздел "Аварийный вход" ниже). Поэтому приватный ключ копируется в менеджер паролей или на второй носитель, а вход через VNC проверяется **до** шага 6.
3. **Панель Contabo (new.contabo.com) остаётся отдельной дверью.** Если сервер заказан в аккаунте другого человека, он по-прежнему может переустановить систему или сбросить пароль root через панель, минуя все настройки ниже. Требуется: перенести услугу в собственный аккаунт Contabo либо сменить в аккаунте почту и пароль, и включить двухфакторную защиту (код из приложения-аутентификатора при входе). Точный порядок переноса уточняется в поддержке Contabo.
4. **Переустановка стирает все данные на сервере.** Общее поручение "следуй инструкции" переустановку не разрешает. Она выполняется только по прямому решению владельца для конкретного сервера, после проверки, что нужные данные скопированы.

## Шаг 0. Свой SSH-ключ

Выполняется на своём компьютере один раз. Если ключ `~/.ssh/id_ed25519` уже есть, шаг пропускается (проверка: `ls ~/.ssh/id_ed25519.pub`).

```bash
# человек, ноутбук (macOS, Linux, Windows 10+ PowerShell): парольную фразу вводит человек
ssh-keygen -t ed25519 -C "<имя>-laptop"
```

На вопрос о пути нажать Enter. Задать парольную фразу (пароль на сам ключ): она защищает ключ, если ноутбук попадёт в чужие руки.

Показать публичную часть:

```bash
# ноутбук, macOS / Linux
cat ~/.ssh/id_ed25519.pub
# ноутбук, Windows PowerShell
type $env:USERPROFILE\.ssh\id_ed25519.pub
```

Проверка: выводится одна строка вида `ssh-ed25519 AAAA... <имя>-laptop`. Эта строка и есть публичный ключ, её можно копировать и отправлять. Файл `id_ed25519` без `.pub` не копируется и не отправляется никуда.

## Шаг 1. Проверка системы и вход в панель

Сервер уже установлен владельцем с Ubuntu 24.04 или 26.04. Инструкция работает на обеих версиях, переустановка не нужна. Образ меняется только по прямому решению владельца для конкретного сервера: общее поручение "следуй инструкции" его не заменяет. Если решение о переустановке принято, перед ней убедиться, что нужных данных на сервере нет, и выбирать образ **Ubuntu 24.04** или **26.04** в панели (**VPS**, меню "More", **Reinstall**, поле **Application** пустое).

1. Войти в панель: <https://new.contabo.com> (человек).
2. Найти нужный сервер, сверить его IP-адрес с `<IP-адрес сервера>`. Ошибиться сервером здесь значит настроить чужой.
3. Найти в панели вход в консоль VNC (раздел управления VPS, пункт VNC) и записать в менеджер паролей данные для VNC: у Contabo они отдельные от пароля root. Если VNC-пароль не задан, задать его там же (человек).

Проверка шага: IP-адрес в панели совпадает с адресом из письма, данные VNC сохранены в менеджере паролей.

## Шаг 2. Первый вход

```bash
# ноутбук
ssh root@<IP-адрес сервера>
```

На вопрос `Are you sure you want to continue connecting (yes/no/[fingerprint])?` перед ответом сверить отпечаток (см. ниже "Проверка отпечатка сервера"). Если вход по паролю `root` из письма Contabo ещё работает, ввести пароль (человек).

Проверка: приглашение изменилось на `root@<имя-хоста>:~#`. Версия системы:

```bash
# администратор
cat /etc/os-release
```

В строке `VERSION_ID` стоит `"24.04"` или `"26.04"`. Другая версия: остановиться и спросить владельца.

### Проверка отпечатка сервера

Отпечаток (fingerprint) ключа сервера защищает от подключения к чужой машине. Пока сервер не менялся, ответ `yes` допустим после сверки. Сверка: в консоли VNC (шаг 1, под root) выполнить

```bash
# человек, консоль VNC
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

и сравнить результат с отпечатком, который показал `ssh` на ноутбуке. Совпало: ответить `yes`.

Если позже соединение сообщает `REMOTE HOST IDENTIFICATION HAS CHANGED`: продолжать только после подтверждённой переустановки нужного VPS. Через консоль Contabo получить отпечаток командой выше, сравнить с новым отпечатком SSH, и только после совпадения удалить старую запись (`ssh-keygen -R <IP-адрес сервера>` на ноутбуке). Причиной может быть неправильный IP-адрес или подмена сервера. Неожиданная смена ключа означает остановку установки и вопрос владельцу.

## Шаг 3. Сменить пароль root и обновить систему

```bash
# человек: пароль вводится вручную и в переписку с агентом не попадает
passwd
```

```bash
# администратор
apt update && apt full-upgrade -y
```

`passwd` дважды спрашивает новый пароль. Новый пароль отличается от прежнего, длинный, хранится в менеджере паролей. После шага 6 он нужен для консоли VNC в панели Contabo (аварийный вход).

Если после обновления появился файл-признак перезагрузки, перезагрузить сервер:

```bash
# администратор
test -f /var/run/reboot-required && reboot
```

Через минуту подключиться снова (`ssh root@<IP-адрес сервера>` с ноутбука).

Проверка: `apt list --upgradable 2>/dev/null | wc -l` печатает 1 или 0 (одна строка заголовка).

## Шаг 4. Свой пользователь с sudo

```bash
# человек: adduser спрашивает пароль, он вводится вручную
adduser <имя>
```

```bash
# администратор
usermod -aG sudo <имя>
```

`adduser` спрашивает пароль (его запрашивает `sudo`, задать надёжный, сохранить в менеджере паролей) и необязательные данные (Enter пропускает).

Проверка:

```bash
# администратор
id <имя>
```

В выводе есть `27(sudo)` (число группы может отличаться, важно слово sudo).

## Шаг 5. Положить свой публичный ключ

Вариант А (с своего компьютера, пока вход по паролю ещё включён):

```bash
# человек, ноутбук: запрашивается пароль пользователя <имя> из шага 4
ssh-copy-id -i ~/.ssh/id_ed25519.pub <имя>@<IP-адрес сервера>
```

В Windows PowerShell `ssh-copy-id` отсутствует. Вариант Б подходит для любой системы.

Вариант Б (администратор, под root). Публичная ключ-строка из шага 0 подставляется вместо `<строка публичного ключа>` целиком, одной строкой:

```bash
# администратор
install -d -m 700 -o <имя> -g <имя> /home/<имя>/.ssh
tee -a /home/<имя>/.ssh/authorized_keys >/dev/null <<'EOF'
<строка публичного ключа>
EOF
chown <имя>:<имя> /home/<имя>/.ssh/authorized_keys
chmod 600 /home/<имя>/.ssh/authorized_keys
```

**Проверка (обязательная до шага 6).** Открыть второй терминал на своём компьютере, не закрывая первый:

```bash
# человек, ноутбук: парольную фразу ключа и пароль для sudo вводит человек
ssh <имя>@<IP-адрес сервера>
sudo -v
```

Вход проходит без запроса пароля пользователя (спросить может парольную фразу ключа, это нормально), а `sudo -v` принимает пароль пользователя без ошибки. Пока это не работает, шаг 6 не выполняется: иначе на сервер не удастся войти вообще.

**Проверка аварийного входа (обязательная до шага 6).** Это вход на сервер без SSH, который понадобится, если ключ потерян или SSH сломан (человек):

1. В панели Contabo открыть консоль VNC сервера (шаг 1) и войти данными VNC из менеджера паролей.
2. В консоли ввести логин `<имя>` и пароль Linux из шага 4. Приглашение `<имя>@<имя-хоста>:~$` означает, что вход работает.
3. Выйти из консоли (`exit`).

Данные VNC и пароль Linux хранятся в менеджере паролей отдельными записями. Без этой проверки шаг 6 не выполняется: консоль для чужих рук ограничена паролем, а не ключом, и надёжный пароль пользователя `<имя>` тут важен.

## Шаг 6. Отключить вход по паролю и вход под root

Дальше команды выполняются в сессии `<имя>` (не под root), с `sudo`.

Настройки SSH-сервера читаются из файлов в каталоге `/etc/ssh/sshd_config.d/`. Каждый файл-дополнение (drop-in) переопределяет значения по умолчанию, не трогая основной файл. Ubuntu читает такие файлы по алфавиту, и **первое найденное значение параметра побеждает**. Облачный образ может содержать файл `50-cloud-init.conf` с разрешённым входом по паролю, поэтому собственный файл получает имя `00-...`, чтобы читаться первым.

```bash
# администратор, сессия <имя>
sudo tee /etc/ssh/sshd_config.d/00-hardening.conf >/dev/null <<'EOF'
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
PubkeyAuthentication yes
MaxAuthTries 3
EOF
sudo sshd -t && sudo systemctl restart ssh
```

`sshd -t` проверяет синтаксис: если он печатает ошибку, перезапуск не выполняется, и сервер остаётся доступным. В Ubuntu служба называется `ssh`, а не `sshd`.

Проверка действующих значений (а не только содержимого файла):

```bash
# администратор
sudo sshd -T | grep -E '^(passwordauthentication|kbdinteractiveauthentication|permitrootlogin|pubkeyauthentication|port) '
```

Ожидается (порядок строк может отличаться):

```
permitrootlogin no
pubkeyauthentication yes
passwordauthentication no
kbdinteractiveauthentication no
port 22
```

Строка `port` показывает реальный порт SSH. Если там не 22, правило межсетевого экрана в шаге 7 пишется для этого порта.

Проверка снаружи, **в третьем терминале**, пока второй остаётся открытым:

```bash
# ноутбук
ssh root@<IP-адрес сервера>
ssh -o PubkeyAuthentication=no <имя>@<IP-адрес сервера>
```

Обе команды обязаны закончиться на `Permission denied (publickey)`. Обычный `ssh <имя>@<IP-адрес сервера>` продолжает работать. Если обычный вход сломан, чинить из ещё открытой сессии: удалить файл `/etc/ssh/sshd_config.d/00-hardening.conf` и снова выполнить `sudo systemctl restart ssh`.

## Шаг 7. Межсетевой экран (ufw): открыт только SSH

**ufw** (uncomplicated firewall): программа, которая закрывает все входящие порты, кроме явно разрешённых. Агентам входящие подключения не нужны: Telegram, Claude и Codex работают через исходящие соединения.

Порядок важен: правило для SSH создаётся **до** включения экрана, иначе соединение оборвётся.

```bash
# администратор. Порт 22 заменить на реальный порт SSH из шага 6, если он другой.
# Если ufw не установлен: sudo apt install -y ufw
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 22/tcp comment 'ssh'
sudo ufw enable
```

На вопрос о возможном обрыве SSH-соединений ответить `y` (правило для порта 22 уже создано).

Проверка:

```bash
# администратор
sudo ufw status verbose
```

Ожидается `Status: active`, `Default: deny (incoming), allow (outgoing)` и строки `22/tcp ALLOW IN Anywhere` (для IPv4 и IPv6). Затем в новом окне терминала `ssh <имя>@<IP-адрес сервера>` продолжает работать.

В панели Contabo есть собственный внешний межсетевой экран (раздел Firewall). Он не обязателен: ufw уже закрывает порты, а два слоя правил усложняют поиск причины, если что-то перестанет открываться.

## Шаг 8. Автоматические обновления безопасности

```bash
# администратор
sudo apt install -y unattended-upgrades
sudo tee /etc/apt/apt.conf.d/20auto-upgrades >/dev/null <<'EOF'
APT::Periodic::Update-Package-Lists "1";
APT::Periodic::Unattended-Upgrade "1";
Unattended-Upgrade::Automatic-Reboot "false";
EOF
```

Ubuntu по умолчанию ставит этим способом только исправления безопасности. Автоматическая перезагрузка остаётся выключенной намеренно: она убила бы запущенных агентов посреди работы. Перезагрузка выполняется вручную, когда агенты простаивают.

Проверка:

```bash
# администратор
systemctl is-enabled unattended-upgrades
systemctl list-timers --all apt-daily.timer apt-daily-upgrade.timer
sudo unattended-upgrade --dry-run --debug
echo "код завершения: $?"
```

Первая команда печатает `enabled`. Вторая показывает оба таймера с ближайшим временем запуска (включённая служба сама по себе не доказывает, что таймеры работают). Третья читается целиком, без обрезки вывода: в нём нет строк `ERROR`, а код завершения равен 0. Запрет автоматической перезагрузки записан явно строкой `Automatic-Reboot "false"`, а не взят из настроек образа. Признак того, что обновление ждёт перезагрузки: файл `/var/run/reboot-required`. Проверять раз в неделю: `test -f /var/run/reboot-required && echo "нужна перезагрузка"`.

## Шаг 9. fail2ban: бан за подбор пароля

**fail2ban** следит за журналом входов и временно блокирует адреса, с которых много раз подряд вводили неверные данные. Вход по паролю уже выключен, но подбор всё равно засоряет журнал и нагружает сервер.

```bash
# администратор
sudo apt install -y fail2ban
sudo tee /etc/fail2ban/jail.local >/dev/null <<'EOF'
[sshd]
enabled = true
backend = systemd
maxretry = 5
findtime = 10m
bantime = 1h
EOF
sudo systemctl enable --now fail2ban
sudo systemctl restart fail2ban
```

Проверка:

```bash
# администратор
sudo fail2ban-client status sshd
```

Ожидается блок `Status for the jail: sshd` со строками `Currently failed` и `Currently banned`. Через несколько часов после запуска `Total banned` обычно больше нуля: в интернете подбор идёт постоянно.

Если свой адрес попал в бан (несколько неудачных попыток подряд), снять бан можно из консоли VNC в панели Contabo (раздел "Аварийный вход" ниже): `sudo fail2ban-client set sshd unbanip <свой IP>`.

## Шаг 10. Часовой пояс

Часовой пояс нужен, чтобы время в журналах и расписаниях совпадало с временем владельца.

```bash
# администратор
timedatectl list-timezones | grep -i <город>
sudo timedatectl set-timezone <Регион/Город>
```

Например, `Europe/Moscow` или `Asia/Almaty`.

Проверка:

```bash
# администратор
timedatectl
```

В строках `Time zone` виден выбранный пояс, `System clock synchronized: yes` и `NTP service: active` (часы сверяются по сети сами).

## Итоговая проверка шага

Все пункты выполняются из нового терминала на своём компьютере и на сервере:

| Проверка | Ожидание |
|---|---|
| `ssh <имя>@<IP-адрес сервера>` | вход без пароля пользователя |
| `ssh root@<IP-адрес сервера>` | `Permission denied (publickey)` |
| `sudo ufw status` | active, открыт только 22/tcp |
| `systemctl is-active fail2ban` | `active` |
| `systemctl is-enabled unattended-upgrades` | `enabled` |
| `timedatectl \| grep 'Time zone'` | нужный пояс |
| вход через консоль VNC в панели Contabo | работает (проверено до шага 6) |

## Аварийный вход: доступ без переустановки

Сброс пароля root в панели Contabo не возвращает SSH, пока в настройках стоят `PermitRootLogin no` и `PasswordAuthentication no`. Переустановка стирает все данные и нужна только по прямому решению владельца. Доступ восстанавливается через консоль VNC (человек): в панели открыть VNC сервера, войти как `<имя>` (пароль Linux из шага 4) и выполнить нужное из списка.

```bash
# человек, консоль VNC, пользователь <имя>

# ключ потерян или заменён: записать новую публичную строку
sudo install -d -m 700 -o <имя> -g <имя> /home/<имя>/.ssh
sudo tee -a /home/<имя>/.ssh/authorized_keys >/dev/null <<'EOF'
<строка нового публичного ключа>
EOF
sudo chown <имя>:<имя> /home/<имя>/.ssh/authorized_keys
sudo chmod 600 /home/<имя>/.ssh/authorized_keys

# SSH сломан настройкой: проверить синтаксис и перезапустить
sudo sshd -t && sudo systemctl restart ssh

# собственный адрес попал в бан fail2ban
sudo fail2ban-client set sshd unbanip <свой IP>

# мешает правило межсетевого экрана: вернуть правило для SSH
sudo ufw allow 22/tcp
```

После восстановления проверить вход по SSH с ноутбука новым терминалом (`ssh -o IdentitiesOnly=yes -i ~/.ssh/id_ed25519 <имя>@<IP-адрес сервера>`). Если и VNC недоступна, обращаться в поддержку Contabo: справка "I can't connect to my server, what do I do?" (help.contabo.com).
